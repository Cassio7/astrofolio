# Where Did My Global Packages Go?

A new Node version comes out, so you do the responsible thing: `nvm install`, switch to it, done.

Except it's not done. With **nvm**, every Node version lives in its own folder, with its own global packages. New version, empty folder. Everything you installed globally over the months stays behind in the old one, and the new one starts from zero.

So now you have to migrate. Easy, right? Just reinstall everything. But... what was everything?
`typescript` for sure. `pnpm`, obviously. `nodemon`, I think? Then the Angular CLI, `pm2`, that formatter I installed once for a single project... and probably something else I'll only remember three days later, exactly when I need it, when the terminal answers with a nice `command not found`.

## The problem

To be fair, nvm does have an option for this: `--reinstall-packages-from`. The catch is that you have to remember it _while_ installing the new version. And let's be honest, I never do. I remember it a week later, when I've already reinstalled half of my packages by hand.

But the real problem for me wasn't the copying. It was that I had no idea what I actually had. After a couple of years of nvm, I had four or five Node versions on my machine, each one with its own little pile of packages. Which one had the right `tsc`? Was that old CLI still installed somewhere, or did I lose it two upgrades ago? And while I was at it, was any of that stuff outdated, or even deprecated?

The only way to find out was the manual one: `nvm use 20`, `npm ls -g`, write it down. `nvm use 22`, `npm ls -g`, write it down. And then compare the lists by eye, like a spot-the-difference game in a puzzle magazine. It works, but it's slow, it's boring, and it's exactly the kind of thing a developer should never do twice xD

So I did what every developer does: instead of solving it in five minutes, I built a tool.

## Meet nvmem

**nvmem** (_nvm_ + _memory_) does one thing: it shows you what's installed in every Node version, and helps you copy it to the next one.

This is what plain `nvmem` looks like: every Node version, its global packages, and the commands each one adds.

![nvmem output: every Node version with its global packages](/og-images/projects/nvmem.png)

```bash
nvmem                  # every version and its global packages, as a tree
nvmem --table          # package × version matrix
nvmem diff 24 26       # what 24 has that 26 doesn't, plus the command to install it
nvmem which tsc        # which versions have it
nvmem -u               # also check npm for updates and deprecations
```

The part I use the most is `diff`. It doesn't just tell you what's missing, it prints the exact `npm install -g` command to fix it, so you can copy and paste it, or run it directly:

```bash
eval "$(nvmem diff 24 26 --command-only)"
```

New Node version, one command, and all my tools are back.

## Why Rust?

At work I write TypeScript every day, with NestJS and Angular. So the obvious choice would have been a small Node script. But here's the joke: **a tool that fixes your Node setup shouldn't depend on your Node setup.** If your current Node version is the broken or empty one, a Node-based tool is the first thing that stops working.

Rust solved that, and gave me a few nice extras:

- **One single binary.** No runtime, no `node_modules`, nothing to install first. You download one file and it works, on macOS, Linux and Windows.
- **Fast.** nvmem doesn't call `nvm` or `npm` at all. It reads nvm's folders directly from disk, so the full list shows up instantly instead of waiting for `npm ls -g` once per version.
- **It made me learn something new.** Going from TypeScript to Rust is not a walk in the park. The compiler is strict, and at the beginning it feels like it's arguing with you about everything. But once the code compiles, it usually just works, and that feeling is pretty addictive.

## Small tool, serious care

Even if it's a small project, it's something people install with a one-line `curl | sh`, and that comes with responsibility. So I tried to do things properly:

- It's **offline by default**. It only talks to the npm registry when you ask for it with `-u`, so your list of packages stays on your machine.
- The install scripts **verify every download with a SHA256 checksum**.
- Release binaries come with a **signed build attestation**, proving they were built on GitHub from the real source code.
- Package names are validated before they end up in a shell command, because a tool that prints commands for you to `eval` shouldn't be the reason something weird gets executed.

Probably overkill for a package lister. But if I'm asking people to trust my binary, it's the least I can do.

## Try it

```bash
# macOS / Linux
curl -fsSL https://raw.githubusercontent.com/Cassio7/nvmem/main/install.sh | sh
```

```powershell
# Windows (PowerShell)
irm https://raw.githubusercontent.com/Cassio7/nvmem/main/install.ps1 | iex
```

The project is open source on [GitHub](https://github.com/Cassio7/nvmem), under the MIT license. It only supports nvm and nvm-windows for now, so no fnm, Volta or asdf, at least not yet.

If you try it, let me know what you think. Issues, ideas and stars are all welcome, and if it saves you even one `command not found` after a Node update, my job here is done.
